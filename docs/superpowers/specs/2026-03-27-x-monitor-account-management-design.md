# 2026-03-27 X Monitor 账号管理改造设计

## 1. 背景

当前 `X Monitor` 的账号列表由 `X_MONITOR_ACCOUNTS_FILE` 驱动，后端在刷新前把文件内容同步到 `x_account` 表。这个结构能支撑只读展示和定时抓取，但不适合“我自己在页面里随时增删监控账号”的使用方式，因为：

- 页面没有账号写入口，只有只读展示。
- 数据库不是运行时真相源，刷新时会被文件重新覆盖。
- 一旦账号数量上升，缺少分层、启停和导入导出能力，监控噪音会快速累积。

本轮目标是把 `X Monitor` 升级成“可维护监控名单的运营台”，优先满足用户手动增删账号，再在展示层做最小必要的分层和筛选。

## 2. 目标与非目标

### 2.1 目标

- 支持在 `X Monitor` 页面直接新增、编辑、启停、删除监控账号。
- 让数据库成为运行时账号真相源，不再在每次刷新前被 JSON 文件覆盖。
- 保留 JSON 文件能力，但改为“初始化 + 导入/导出”，而不是强同步来源。
- 为账号增加轻量分层字段，支持 `core` / `watch` / `muted` 三层。
- 默认帖子流优先展示高层级账号内容，降低账号扩容后的噪音。

### 2.2 非目标

- 本轮不做自动推荐账号。
- 本轮不做账号质量自动打分或命中率回灌。
- 本轮不把 X 内容并入新闻主链路。
- 本轮不引入复杂权限、多用户协作或审计系统。

## 3. 方案选择

### 方案 A：继续以 JSON 文件为单一真相源

优点：

- 最贴近现有结构。
- 文件可直接 git 跟踪。

缺点：

- 页面增删改需要并发写文件，后端复杂度高。
- 运行中刷新会持续覆盖数据库编辑结果。
- 后续扩展层级、状态、导入导出会越来越别扭。

### 方案 B：数据库为单一真相源，JSON 仅作示例

优点：

- 页面增删改最自然。
- 后续扩字段和统计最顺手。

缺点：

- 失去显式文件化名单，不利于备份和跨环境迁移。

### 方案 C：数据库为运行真相源，JSON 用于初始化与导入导出

优点：

- 页面维护体验最好。
- 保留文件化资产，便于备份和迁移。
- 和当前仓库结构兼容，改造范围可控。

缺点：

- 需要定义清楚导入导出语义，避免“谁覆盖谁”混乱。

### 方案结论

采用方案 C：

- `x_account` 为运行时真相源。
- 启动后若数据库为空且配置文件存在，可显式执行一次导入初始化。
- 页面日常增删改只操作数据库。
- 用户需要文件化时，通过导出接口回写 JSON。

## 4. 数据模型设计

### 4.1 `x_account`

在现有字段基础上新增：

- `tier`: `core | watch | muted`
- `source`: `file_import | manual`

现有字段继续保留：

- `handle`
- `display_name`
- `market_focus`
- `is_active`
- `priority`
- `notes`

约束：

- `handle` 仍为唯一键，统一去掉前导 `@`。
- `tier` 默认 `watch`。
- `source` 默认 `manual`。

### 4.2 配置文件结构

账号文件继续保留 `accounts` 数组，但允许携带新字段：

- `tier`
- `source`

导出时统一按 `priority desc, handle asc` 排序，保证 diff 稳定。

## 5. API 设计

新增或调整以下接口：

- `GET /api/x/accounts`
  - 返回完整账号列表，支持页面展示和编辑。
- `POST /api/x/accounts`
  - 新增账号。
- `PATCH /api/x/accounts/{handle}`
  - 更新显示名、市场、优先级、tier、notes、启停状态。
  - `handle` 作为唯一标识，不支持重命名；输错时走“删除后重建”。
- `DELETE /api/x/accounts/{handle}`
  - 删除账号。
- `POST /api/x/accounts/import`
  - 从配置文件显式导入账号到数据库。
- `POST /api/x/accounts/export`
  - 将当前数据库账号导出到配置文件。

保持现有接口：

- `GET /api/x/posts`
- `POST /api/x/refresh`
- `GET /api/x/search`

## 6. 后端行为变更

### 6.1 刷新行为

当前 `refresh()` 的“先从文件同步账号”改为：

1. 直接读取数据库中的 active 账号。
2. 若数据库为空且配置文件存在，不自动覆盖；只在显式导入时写入。
3. `muted` 是“保留账号元数据但默认不抓取”的 ingest 层级，不等同于 `is_active=false`。
4. 抓取时仅处理 `is_active=true` 且 `tier != muted` 的账号，并按 `core` 优先、`watch` 次之排序。

### 6.2 导入行为

- 从配置文件读取账号列表。
- 对已存在 `handle` 做 upsert。
- 本轮导入语义定义为“merge-only”：
  - 文件中存在的账号会新增或更新。
  - 数据库中存在但文件中缺失的账号不会被自动删除。
  - 删除必须通过页面删除，避免文件导入误删运行中账号。
- 导入来源统一覆盖为 `file_import`，不信任文件中的 `source` 字段。
- 返回导入统计：新增、更新、跳过数量。

### 6.3 导出行为

- 将数据库账号按稳定顺序写回账号文件。
- 导出不改变数据库内容。
- 写文件采用完整覆盖写入，避免局部残留。
- 导出保留数据库中的 `source` 字段，作为当前运行状态快照。

### 6.4 现有数据库兼容

- 现有项目数据库可能已经存在旧版 `x_account` 表。
- 初始化流程需要补充缺失列：
  - `tier`
  - `source`
- 对旧数据做一次兼容回填：
  - `tier` 默认 `watch`
  - `source` 默认 `manual`

## 7. 前端设计

页面保留当前三块区域，但左侧“状态与筛选”升级为“状态与账号管理”：

- 顶部仍显示 provider 状态和刷新策略。
- 增加账号列表，支持：
  - 新增账号
  - 编辑 display_name / tier / priority / market / notes
  - 启用/停用
  - 删除
- 增加导入与导出按钮。

帖子流默认规则：

- 默认只展示 `core + watch` 的 active 账号帖子。
- 页面增加按 `tier` 筛选。
- 账号列表里明确显示 `core/watch/muted` 标识。

## 8. 测试策略

后端：

- 账号 CRUD API 测试。
- 导入/导出测试。
- 刷新不再依赖文件强同步的回归测试。
- `muted` 不参与抓取，`core/watch` 参与抓取的测试。

前端：

- 页面可新增账号并刷新列表。
- 可编辑和删除账号。
- 导入导出按钮触发对应 API。
- 分层标签和筛选正确渲染。

## 9. 风险与后续

- 导出覆盖配置文件时需确保格式稳定，否则会造成无意义 diff。
- 如果用户在页面和文件同时修改，规则如下：
  - 显式导入只会合并文件中的账号到数据库，不会删除数据库现有账号。
  - 显式导出会用当前数据库状态完整覆盖账号文件。
- 后续可继续追加“账号质量指标”和“按层级分别刷新频率”，但不应混入本轮实现。
