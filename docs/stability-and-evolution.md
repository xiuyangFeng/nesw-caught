# 稳定性与演进规范

## 1. 稳定性原则

- 外部源不可靠是常态，不是例外
- 任一处理步骤失败都应可记录、可重试、可降级
- 延迟必须可见，不得伪装成“实时”
- AI 结果只作为辅助信号，不作为唯一判断依据
- 增强组件必须可关闭，不影响基础能力

## 2. 最低运行保障

### 日志

- 采集日志
- 正文抓取日志
- 行情刷新日志
- 数据源健康日志
- 单向推送连接和广播日志
- 异常日志

### 指标

- RSS 抓取成功率
- 正文抓取成功率
- 单次抓取耗时
- 单向推送活跃连接数
- 最近新闻入库延迟
- 行情最近刷新时间
- FTS 索引大小和数据库文件大小

### 失败处理

- RSS 抓取失败：记录失败并进入下个周期
- 正文抓取失败：标记状态，可手动或自动重试
- 行情拉取失败：保留上一份快照并标注过期
- 单向推送失败：自动重连并回退到轮询刷新
- 本地 LLM 不可用：退回基线情绪或规则方案

## 3. 测试策略

### 单元测试

- URL 规范化
- 新闻去重
- 情绪分值映射
- 主题聚合规则

### 集成测试

- RSS 解析到入库
- 正文抓取到更新
- 股票提及识别到关联落库
- 行情拉取到异动判断
- 单向推送事件广播

### 回放测试

保留一组历史 RSS 样本和行情样本，用于回归测试，避免数据源变化直接破坏链路。

同时保留不同市场和时区样本，专门验证排序和展示正确性。

## 4. AI 演进规范

### 第一阶段

- 先预留接口，不强依赖 AI
- AI 结果写入独立字段或独立表
- 前端明确标注“AI 生成”
- 本地 LLM 和远程模型都要支持禁用

### 第二阶段

- AI 摘要
- 利好利空解释
- 自选股相关新闻总结
- 异常事件自然语言告警

## 5. 通知演进规范

后续通知能力统一基于 `signal_event` 扩展，避免各通道直接读取业务表。

通知通道建议顺序：

1. 站内通知
2. 邮件
3. Telegram 或企业微信

## 6. 开发流程建议

- 每个阶段先写验收口径，再写实现
- 所有外部源先做最小可用接入，再做站点适配优化
- 每新增一个数据源，都要补异常案例
- 每新增一个智能判断，都要保留原始依据和回退路径
- 每新增一个时间字段，都要说明其 UTC 存储和展示时区规则

## 7. 运维自治

### 健康检查

提供统一健康检查接口，至少包含：

- 数据库状态
- 最近 RSS 抓取时间
- 最近行情刷新时间
- 数据源健康汇总
- 推送连接数
- AI 服务状态

### 备份和清理

- 使用定时任务执行 SQLite 备份
- 保留最近若干份备份
- 对 `news_item`、`article_content` 和 `price_snapshot` 执行保留期清理
- 清理策略默认保守，优先归档，避免误删

- 安全与威胁建模类 skill
- 自动化测试和页面回归类 skill
