## 1. 数据模型：补齐关键关联与生命周期

### 1.1 缺失的"新闻 ↔ 股票"关联表

当前模型中 `news_item` 和 `watchlist_item` 之间没有显式的关联。然而"某条新闻和我的自选股有没有关系"恰恰是产品需求文档里的第三个核心问题。

**建议**：新增 `news_stock_mention` 关联表：

```text
news_stock_mention
├── id
├── news_id         → news_item.id
├── symbol          → watchlist_item.symbol
├── market
├── mention_type    (title / body / inferred)
├── confidence      (0.0 ~ 1.0)
└── created_at
```

这张表由正文抓取或情绪分析步骤填充。有了它，"自选股相关新闻"视图才有数据基础，而不是等到 AI 阶段才能实现。

### 1.2 情绪分数应直接挂在 news_item 上

当前 `sentiment_score` 只出现在 `topic_cluster` 上，但产品需求明确要"为每条新闻生成基础情绪标签"。

**建议**：在 `news_item` 上增加 `sentiment_label`（positive / negative / neutral）和 `sentiment_score`（浮点数）两个字段。`topic_cluster.sentiment_score` 则作为聚合值由子新闻的分数加权得出，而非独立标注。

### 1.3 数据保留与清理策略

文档未提及数据生命周期。SQLite 文件会持续膨胀——以每日 500 条新闻估算，半年后 `article_content` 的正文字段将占据数百 MB。

**建议**：
- 定义保留策略：例如 `news_item` 保留 180 天，`price_snapshot` 保留 90 天，`article_content` 中超过 90 天的正文压缩或归档
- 在 `scheduler` 中加入每日执行的 `cleanup_task`
- 清理前执行 `VACUUM` 或使用增量清理避免长时间锁表

### 1.4 数据源健康追踪表

文档多次提到"数据源不可靠是常态"，但缺少结构化的健康追踪。

**建议**：新增 `source_health` 表：

```text
source_health
├── id
├── source_name
├── source_type       (rss / api / scraper)
├── last_success_at
├── last_failure_at
├── consecutive_failures
├── total_fetches
├── total_failures
├── avg_latency_ms
└── is_disabled
```

当 `consecutive_failures` 超过阈值时自动降级（增大拉取间隔或暂停），并在 Dashboard 上展示源健康状态。这比单纯靠日志排查要高效得多。

## 2. 后端架构模式：引入进程内事件总线

### 2.1 当前问题

技术架构中的流水线是线性描述（抓取 → 去重 → 正文 → 情绪 → 聚合 → 推送），但实际实现中，各步骤之间的耦合方式没有定义。如果直接用函数调用串联，新增一个处理步骤（比如"股票提及提取"）就需要修改主链路代码。

### 2.2 建议：轻量级进程内事件总线

不需要引入 RabbitMQ 或 Redis，只需在 Python 进程内实现一个简单的发布-订阅机制：

```python
# 伪代码示意
class EventBus:
    def publish(self, event_type: str, payload: dict): ...
    def subscribe(self, event_type: str, handler: Callable): ...

# 注册处理器
bus.subscribe("news.created", extract_article_content)
bus.subscribe("news.created", extract_stock_mentions)
bus.subscribe("article.extracted", run_sentiment_analysis)
bus.subscribe("sentiment.scored", update_topic_cluster)
bus.subscribe("topic.updated", broadcast_ws_event)
```

**收益**：
- 新增处理步骤只需注册新的订阅者，不修改已有代码
- 每个处理器可以独立失败和重试，不阻塞其他步骤
- 天然适配未来的 AI 模块——只需订阅 `article.extracted` 事件即可

### 2.3 任务调度的幂等性

`scheduler` 模块的描述比较笼统。在实际运行中，如果定时任务执行超时与下一次触发重叠，可能出现重复抓取。

**建议**：
- 每个定时任务使用分布式锁（SQLite 场景下用文件锁或数据库行锁即可）
- 每次抓取任务携带一个 `batch_id`，去重判断时包含 `batch_id` 以避免同一轮次的并发冲突
- 使用 APScheduler 的 `max_instances=1` 配置确保同一任务不并行

## 3. 采集层韧性：分级策略与自愈机制

### 3.1 抓取频率应当分级而非统一

当前设计对所有 RSS 源似乎使用统一的抓取间隔。但港股和美股的交易时段不同，盘中和盘外的信息密度差异巨大。

**建议**：实现三级频率策略：

| 场景 | RSS 间隔 | 行情间隔 |
|------|---------|---------|
| 对应市场盘中 | 1-2 分钟 | 1 分钟 |
| 对应市场盘前/盘后 | 5 分钟 | 5 分钟 |
| 非交易日/深夜 | 15-30 分钟 | 暂停 |

配置可以在 `settings` 中声明交易日历（港股和美股各一份），`scheduler` 根据当前时间自动选择对应频率。这既节省资源，又能在关键时段提供更好的实时性。

### 3.2 正文抓取的退避与放弃策略

文档提到"正文失败可重试"，但没有定义退避策略。

**建议**：
- 使用指数退避：失败后等待 1 分钟、5 分钟、30 分钟再分别重试
- 最多重试 3 次，之后标记为 `extract_status = 'permanently_failed'`
- 对于已知反爬严格的域名（可维护一个黑名单），直接跳过正文抓取，只保留 RSS 摘要
- 记录每个域名的抓取成功率，成功率低于 30% 的域名自动降级

### 3.3 请求层统一封装

所有对外 HTTP 请求（RSS、正文、行情 API）应共享一个统一的请求客户端：

- 统一 User-Agent 管理和轮换
- 统一超时设置（建议 RSS 10s、正文 15s、行情 API 5s）
- 统一请求速率限制（per-domain rate limiter），避免被同一站点封禁
- 统一代理配置入口（后续如果某些源需要代理，只需改配置）

## 4. 前端工程：状态管理与用户体验

### 4.1 实时数据的前端状态分层

前端同时存在三种不同更新频率的数据：新闻流（分钟级）、行情数据（秒/分钟级）、主题聚合（小时级）。如果混在同一个 store 中，更新频率高的数据会导致低频组件不必要地重渲染。

**建议**：将 Pinia store 按更新频率拆分：

```text
stores/
├── newsStore        → 新闻流，增量追加
├── marketStore      → 行情快照，高频覆盖
├── topicStore       → 主题聚合，低频更新
├── watchlistStore   → 自选股配置，手动变更
└── connectionStore  → WebSocket/SSE 连接状态
```

### 4.2 离线容错与乐观更新

作为长期使用的本地工具，后端重启或临时不可用是常见场景。

**建议**：
- 前端维护一份最近数据的内存缓存，后端断开时继续展示已有数据并显示"数据可能已过期"横幅
- 自选股的增删操作使用乐观更新——先更新 UI，后台发请求，失败再回滚
- 连接状态在页面顶部用颜色指示器常驻显示（绿/黄/红）

### 4.3 新闻流的虚拟滚动

新闻流会随时间积累。如果 DOM 中渲染了数百条新闻卡片，页面性能会显著下降。

**建议**：从第一天就对新闻列表使用虚拟滚动（Vue 生态中可用 `vue-virtual-scroller`），只渲染可视区域内的 DOM 节点。这个决定越早做，后期改造成本越低。

## 5. 运维自治：让系统能自我解释

### 5.1 内建健康检查端点

当前文档只在稳定性章节提到了日志和指标，但没有标准化的健康检查机制。

**建议**：提供 `GET /api/health` 端点，返回结构化状态：

```json
{
  "status": "degraded",
  "uptime_seconds": 86420,
  "database": "ok",
  "last_rss_fetch": "2026-03-15T10:30:00Z",
  "last_price_fetch": "2026-03-15T10:31:00Z",
  "rss_sources": { "total": 8, "healthy": 6, "failing": 2 },
  "ws_connections": 1,
  "disk_usage_mb": 245
}
```

这个端点既是前端连接状态指示器的数据源，也是你自己排查问题时的第一入口。

### 5.2 内建数据库备份

SQLite 单文件的特性使备份非常简单，但需要自动化。

**建议**：
- 每日在低峰时段（如凌晨 4 点）使用 SQLite 的 `VACUUM INTO` 命令生成备份文件
- 保留最近 7 份备份，滚动删除
- 备份任务纳入 `scheduler` 统一管理

### 5.3 启动自检

本地长期运行的工具，重启后可能遇到配置变更、数据库 schema 不匹配等问题。

**建议**：在后端启动时执行自检流程：
1. 验证数据库文件存在且 schema 版本匹配
2. 验证所有配置的 RSS 源格式正确
3. 验证至少一个行情数据源可达
4. 如果自检失败，以降级模式启动（只提供已有数据查询，不启动采集任务）

## 6. 对 Gemini 建议的交叉审视

Gemini 的五条建议质量都不错，以下是我的补充看法：

### 6.1 RSSHub（赞同，补充优先级）

完全赞同引入 RSSHub。但建议在 M2 阶段先以原生 RSS 跑通链路，M3 或 M4 阶段再引入 RSSHub。原因是 RSSHub 自部署本身有维护成本（Docker、路由更新），第一阶段应该把精力放在核心流水线上。可以在配置层预留 RSSHub 的 base_url 字段，切换时只改配置。

### 6.2 SQLite FTS5（强烈赞同，建议提前到 M1）

这是投入产出比最高的建议之一。FTS5 是 SQLite 内置能力，不引入任何外部依赖，但能从根本上解决全文检索问题。建议在 M1 阶段建表时就把 FTS5 虚拟表建好，即使前端搜索功能延后，数据从一开始就应该进入索引。

### 6.3 SSE 替代 WebSocket（赞同，有条件）

对于第一阶段单向推送的场景，SSE 确实更简单。但有一点需要注意：如果后续要支持"用户在前端标记某条新闻为已读"或"前端请求刷新某个自选股"这类从客户端到服务端的指令，SSE 需要额外的 REST 请求来补充上行通道。

**我的建议**：第一阶段用 SSE，但在 `connectionStore` 中封装统一的消息层接口，后续需要双向通信时可以平滑切换到 WebSocket 而不改变业务代码。

### 6.4 本地 LLM via Ollama（赞同，但需要定义降级路径）

Ollama + 轻量模型的方案非常适合本地自用场景。但需要考虑：
- 并非所有机器都有足够的 RAM/GPU 跑 8B 模型
- Ollama 服务可能未启动或崩溃

**补充建议**：将 LLM 调用设计为可选增强层，而不是必要依赖。当 Ollama 不可用时，自动回退到关键词匹配的基线方案。配置中用一个 `ai.enabled` 开关控制，并在 health 端点中报告 AI 服务状态。

### 6.5 ATR 动态异动阈值（赞同，建议简化初始实现）

ATR 是专业且合理的方案，但计算 14 日 ATR 需要足够的历史行情数据。第一阶段行情数据可能不完整。

**建议分两步走**：
1. 初期使用"当日涨跌幅绝对值 > 个股默认阈值"的简单方案
2. 当 `price_snapshot` 积累 14 个交易日以上数据后，自动切换到 ATR 方案
3. 在 `watchlist_item` 中保留 `alert_mode` 字段（`fixed` / `atr`），允许逐只股票切换

## 7. 额外建议：被忽视但重要的细节

### 7.1 时区处理规范

产品需求提到"统一时区存储与展示策略"，但技术文档中没有给出具体方案。港股（HKT, UTC+8）、美股（ET, UTC-5/-4，有夏令时）、服务器（可能是任何时区）三者并存。

**建议**：
- 数据库中所有时间字段一律存 UTC
- 后端 API 返回 UTC 时间戳
- 前端根据新闻的 `market` 字段决定展示时区：港股新闻显示 HKT，美股新闻显示 ET
- 行情数据始终显示对应市场时区

### 7.2 配置热更新

当前配置分层的描述偏静态。但在日常使用中，添加一个新的 RSS 源或修改自选股不应该需要重启后端。

**建议**：
- 自选股和 RSS 源配置存入数据库，提供 API 管理，变更即时生效
- 系统级配置（端口、日志级别、数据库路径）保留在文件中，变更需重启
- 在前端提供一个简单的"设置"页面管理动态配置

### 7.3 去重策略的分层增强

当前去重只提到 URL 哈希 + 标题哈希 + 时间窗口。在实际港美股新闻场景中，同一事件会被多个媒体用完全不同的标题报道。

**建议**：实施三层去重：
1. **精确去重**：规范化 URL 哈希完全匹配 → 直接跳过
2. **近似去重**：标题 Simhash 汉明距离 ≤ 3 且发布时间窗口 ≤ 2 小时 → 合并到同一主题
3. **语义去重**（M4+）：正文 embedding 余弦相似度 > 0.85 → 建议合并

前两层在 M2 实现，第三层等 AI 模块就绪后自然接入。
