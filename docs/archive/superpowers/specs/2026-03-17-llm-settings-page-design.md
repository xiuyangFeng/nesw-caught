# LLM 设置页设计

## 背景

当前项目已经支持后端保存单套活动 `LLM` provider 配置，并在新闻详情页手动触发单条新闻分析。但这套配置目前只能通过接口写入，缺少前端入口，不适合后续分享给其他人时自行录入 key 和模型参数。

本轮补一个前端设置页，目标是让“当前活动配置”可以在 UI 中直接查看和更新，同时保持第一版仍然是单活动配置，不扩展成多套 provider 管理后台。

## 目标

- 新增一个独立的 `LLM Settings` 页面。
- 页面展示并编辑当前活动配置：
  - `provider_name`
  - `display_name`
  - `base_url`
  - `model_name`
  - `api_key`
- 保存时直接覆盖当前活动配置。
- 若用户编辑已有配置但不想改 key，允许保留后端已存的 key。
- 新闻详情页继续复用同一套活动配置，不新增第二套状态源。

## 非目标

- 不实现多配置列表、历史版本或多用户隔离。
- 不实现 provider 连通性测试。
- 不在本轮中做 key 加密存储重构。

## 方案

### 1. 新增独立设置页与导航入口

前端新增路由 `/settings/llm`，左侧导航新增 `LLM Settings`。页面风格沿用当前 `SectionCard + 表单 + 状态提示` 组合，不引入新的后台管理风格。

页面结构分两块：

- 配置说明卡片：说明当前设置将影响新闻详情页的手动分析功能
- 活动配置表单：编辑并保存当前 provider 配置

### 2. 设置页采用“单活动配置表单”

页面不展示多条配置记录，只展示“当前正在生效的那一套”。这样直接对应现有后端模型和使用阶段，也避免出现“草稿配置”“切换 active”之类还不需要的概念。

默认交互：

- 页面加载时调用 `GET /api/llm/config`
- 若未配置，表单为空
- 若已配置，填入除 `api_key` 之外的字段
- `api_key` 输入框默认留空并显示占位提示，例如“留空表示保留当前 key”

### 3. 后端更新语义补成“空 key 表示保留”

这是本轮最关键的后端补充。因为 `GET /api/llm/config` 不会回传原始 key，如果前端加载已有配置后直接提交空白 `api_key`，当前实现会把 key 清空，导致设置页无法安全编辑现有配置。

因此 `POST /api/llm/config` 需要改成：

- 新建配置时：`api_key` 必填
- 更新已有配置时：
  - 若传了非空 `api_key`，用新值覆盖
  - 若传空字符串或不传，保留原值

这能让设置页安全地编辑 `provider/model/base_url`，而不强迫用户每次都重新输入 key。

### 4. 前端状态独立为 LLM 设置 store

当前 `llmConfig` 状态挂在 `newsStore` 里，仅够新闻详情页使用。设置页加入后，更合适的结构是新增独立 `llmStore`，统一管理：

- 当前配置
- 加载状态
- 保存状态
- 保存错误
- 保存成功提示

`NewsDetailView` 也改为从 `llmStore` 读取配置，而不是继续从 `newsStore` 取。

### 5. 表单校验尽量轻量

第一版只做最小可用校验：

- `provider_name` 必填
- `model_name` 必填
- 新建配置时 `api_key` 必填
- `base_url` 可为空，但对 `openai-compatible` provider 通常应填写

不做复杂 provider-specific 表单分叉，保留纯文本输入，避免第一版被模板逻辑拖复杂。

## 风险与取舍

- 把 key 保留语义做在后端，可以避免前端误清空配置；代价是 `POST /api/llm/config` 的行为从“全量覆盖”变成“部分保留”，需要测试明确约束。
- 现在还没有后端加密存储，所以设置页虽然可用，但安全边界仍是“单租户内网工具级别”。
- 新增独立 `llmStore` 会让前端结构更清晰，但需要同步改动新闻详情页配置读取逻辑。

## 验证思路

- 后端测试：
  - 新建配置时必须有 key
  - 更新已有配置且 key 留空时保留原值
- 前端测试：
  - 设置页未配置时展示空表单
  - 设置页已配置时回填非敏感字段
  - 保存后展示成功提示
  - 新闻详情页继续能读到配置状态
- 最小回归验证：
  - `conda run -n news-caught pytest backend/tests`
  - `npm --prefix frontend run test -- --run`
  - `npm --prefix frontend run build`
