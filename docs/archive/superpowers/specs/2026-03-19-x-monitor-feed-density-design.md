# X Monitor Feed Density Design

## Context

`X Monitor` 页右侧的“账号监控帖子流”当前按大卡片纵向铺开。帖子一多，整个右侧区块会持续向下增长，导致页面失衡，也让左侧状态与筛选区显得像一个短侧栏。与此同时，单条帖子内边距和正文节奏偏松，同屏可见信息量偏低。

## Problem

- 帖子流没有高度边界，随着数据增多会把页面拉成一条长列。
- 单条帖子卡片占用空间偏大，列表密度不足。
- 当前视觉更像内容阅读卡片，不像监控面板中的高密度列表。

## Goals

- 让右侧帖子流在桌面端保持固定面板高度，不再无限向下延伸。
- 把单条帖子压缩成更偏列表感的紧凑条目，提高同屏信息密度。
- 保留必要信息：账号、时间、市场、情绪、股票命中、原帖链接。
- 在帖子流顶部增加一块更精致的摘要区，文案既体现状态感，也体现当前跟踪规模。

## Non-Goals

- 不改后端接口、store 数据结构或帖子筛选逻辑。
- 不新增帖子展开、折叠、分页或虚拟滚动行为。
- 不改变移动端的基本阅读顺序，只做适配性的高度回退。

## Approaches Considered

### 方案 A：固定高度卡片流

保留现有卡片样式，只给帖子区增加最大高度和内部滚动。

优点：改动最小。
缺点：视觉问题只解决一半，卡片仍显得厚重，信息密度提升有限。

### 方案 B：摘要区 + 列表感帖子流

帖子区顶部加一条精致摘要，下面将帖子改成更扁平的行式列表，整个区域固定高度并内部滚动。

优点：同时解决高度失控和密度不足；右侧视觉会更像实时监控流。
缺点：需要同步调整文案层级、间距和测试断言。

### 方案 C：摘要区 + 仅展示前 N 条

只显示有限条帖子，剩余通过“查看更多”跳转或展开。

优点：高度控制最强。
缺点：会直接损失监控场景下的连续浏览能力，不符合当前页面用途。

## Decision

采用方案 B。

- 右侧 `SectionCard` 内部新增一个摘要条。
- 摘要主句使用状态提示语气，但包含跟踪总量，例如“当前跟踪 24 条帖子，帖子流已同步到最新窗口”。
- 摘要副句承载运行状态信息，例如请求节流、刷新冷却和最近刷新时间。
- 帖子列表容器在桌面端设置固定最大高度并启用内部滚动。
- 单条帖子从厚卡片压缩为列表感条目：更小的 padding、更弱的圆角和阴影、用分隔线区分项、缩短正文字号和行距。

## Interaction

- 桌面端：
  - 右侧帖子流与左侧状态区保持更接近的视觉高度。
  - 超出部分仅在帖子面板内部滚动。
  - 摘要固定在帖子列表顶部，先交代整体状态，再进入具体帖子。
- 移动端：
  - 帖子区取消固定高度，恢复自然流式布局，避免小屏内部滚动区域过窄。

## Data and Rendering

- 继续使用 `xMonitorStore.posts` 作为帖子数据源。
- 在 `XMonitorView.vue` 内新增本地计算属性生成摘要文案：
  - 帖子总数
  - 最近刷新时间文本
  - 已有的节流/冷却状态文本
- 不新增接口字段；摘要总数直接取当前筛选后的帖子数。

## Testing

- 更新 `frontend/src/views/XMonitorView.test.ts`：
  - 校验摘要主句包含当前跟踪帖子数。
  - 校验摘要副句仍展示节流与冷却信息。
  - 校验帖子列表容器和帖子条目使用新的紧凑类名。

## Risks

- 摘要里的帖子数量是当前前端筛选后的可见数量，而不是后端库中的总帖子量；这更符合用户当下看到的列表，但需要避免文案造成“全局总量”误解。
- 固定高度需要兼顾不同屏幕尺寸；若高度过小会影响可读性，过大则会削弱压缩效果，因此应使用响应式 `clamp` 或断点兜底。
