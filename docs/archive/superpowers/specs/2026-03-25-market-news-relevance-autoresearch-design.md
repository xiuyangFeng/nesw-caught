# 市场新闻相关性 AutoResearch 设计

## 背景

当前项目已经具备新闻抓取、入库、信号处理和前端展示链路，但“抓到的新闻是否真的值得进入市场主 feed”仍缺少稳定的研究闭环。现状存在三类问题：

- 抓取链路更偏“尽量多拿”，缺少围绕市场相关性的可量化优化目标
- 每次优化过滤规则、prompt 或 source 配置时，缺少固定评测集，结果容易依赖主观感觉
- 代理虽然可以协助改代码，但还没有一个受控实验框架来决定“这次改动是否真的让市场新闻命中率更好”

用户希望借鉴 `karpathy/autoresearch` 的核心思想，把“代理自己做研究”转化为本项目中的长期能力，但研究范围先收敛到新闻相关性优化，不扩展到前端和基础设施。

## 目标

本轮设计目标如下：

1. 建立一套围绕“市场相关新闻命中率”的固定评测闭环
2. 产出第一版约 `400` 条、可持续扩充的半自动标注数据集
3. 允许代理在受控边界内自动修改新闻抓取和分类相关代码，然后用固定评测集验证效果
4. 把每轮实验沉淀为结构化研究记录，形成项目内可持续迭代的研究账本

## 非目标

- 本轮不做前端改动，也不把研究结果直接映射为 UI 优化
- 不让代理自由改动基础设施、SSE/Redis 事件层、数据库底座或通用运行链路
- 不在第一版就追求复杂多标签体系、在线学习或全自动无人值守长期运行
- 不把外部 `autoresearch` 仓库直接集成为 skill；本轮只迁移其“受控实验”工作方式

## 方案概览

推荐把项目内的“自动研究”拆成五个固定部件：

1. 样本池：从历史数据库新闻和当前 source 实时抓取结果中混合抽样
2. 标注流水线：先走 `DeepSeek` 首轮粗标签，再进入低置信度和抽样人工复核
3. 评测器：基于固定数据集输出 market relevance 相关指标和误判样例
4. 研究代理：仅允许改受控范围内的配置、规则、prompt 和后端相关服务
5. 实验账本：记录每轮实验假设、改动点、指标结果和保留结论

核心原则与 `autoresearch` 一致：

- 不是“让代理自由发挥”，而是“把代理限制在一个可比较、可淘汰的实验循环里”
- 不是“改完看感觉”，而是“固定 baseline、固定数据集、固定指标，再决定保留或丢弃”

## 数据集设计

### 1. 样本来源

第一版评测集规模固定为约 `400` 条，来源使用混合抽样：

- 历史数据库中的 `news_item`
- 当前配置 source 新抓的一批新闻候选

这样做的原因：

- 历史数据可以覆盖真实噪音分布和旧问题
- 新抓样本可以覆盖当前 source 配置下的最新内容分布
- 混合来源可以降低代理只对“历史偏差”或“最新偏差”过拟合的风险

建议第一版样本构成：

- 历史数据库样本：约 `240`
- 实时抓取样本：约 `160`

具体比例允许在实施时微调，但必须保留“两类来源同时存在”的约束。

### 2. 标签体系

第一版只采用粗标签，优先尽快形成稳定闭环：

- `market_relevant`
  - 布尔值，表示该条内容是否值得进入市场主 feed
- `noise_type`
  - 当 `market_relevant = false` 时填写
  - 第一版限制在少量枚举中，避免标注漂移

建议的 `noise_type` 枚举：

- `generic_tech`
- `lifestyle_or_entertainment`
- `duplicate_or_rewrite`
- `low_information`
- `off_topic`
- `other`

这里的“市场相关”明确定义为：

- 与上市公司、行业、宏观政策、监管、财报、交易、融资、并购、供应链冲击、商品价格、汇率、利率或其他会影响投资判断的事件直接相关

以下内容默认不算 `market_relevant`：

- 泛科技资讯但没有明确资本市场含义
- 消费/娱乐/生活方式类文章
- 内容重复、转载痕迹重、信息增量很低的文章
- 与市场事件无直接关系的软文或品牌宣传

### 3. 数据格式

建议新增一份评测数据文件，采用 `jsonl` 或 `json`，每条样本至少包含：

```json
{
  "sample_id": "hist-0001",
  "source_type": "historical",
  "origin": {
    "news_id": 123,
    "source_name": "The Verge",
    "canonical_url": "https://example.com/article",
    "published_at": "2026-03-20T08:30:00Z"
  },
  "content": {
    "title": "Example title",
    "summary": "Example summary",
    "body_excerpt": "Optional short excerpt"
  },
  "labels": {
    "market_relevant": true,
    "noise_type": null
  },
  "annotation": {
    "label_source": "human_reviewed",
    "model_name": "deepseek-chat",
    "confidence": 0.94,
    "review_notes": ""
  }
}
```

约束：

- `sample_id` 必须稳定，不因重新标注而变化
- `origin` 保留足够的追溯信息，便于回放和人工核对
- `annotation.label_source` 需要区分 `model_only`、`human_reviewed`、`human_corrected`

## 半自动标注流水线

### 1. 抽样阶段

新增抽样脚本，从两类来源生成待标注样本池：

- 历史新闻：按时间窗口、来源、市场分布做分层采样
- 实时新闻：触发一次或多次抓取，保留原始候选结果，再抽样进入池子

抽样要求：

- 同一 canonical URL 只保留一个样本
- 需要显式控制 source 分布，避免单一来源淹没数据集
- 需要预留一部分高疑似噪音样本，避免样本集过于“干净”

### 2. 模型首标阶段

使用 `DeepSeek` API 对待标注样本做首轮粗标，输出：

- `market_relevant`
- `noise_type`
- `confidence`
- `reason`

模型提示词需要严格约束：

- 只允许输出固定 schema
- 先判断是否对投资者或市场观察者有直接信息价值
- 再在 `not_relevant` 情况下选择 `noise_type`
- 明确“泛科技热词但无市场事件”不算市场相关

### 3. 复核阶段

首轮模型标注完成后，进入两类复核：

- 必审样本
  - 低置信度样本
  - 模型返回 `other`
  - 标题过短、摘要为空或信息含混的样本
- 抽检样本
  - 从高置信正例和高置信负例各抽一部分做人审

复核后规则：

- 若人工和模型一致，则标为 `human_reviewed`
- 若人工修正模型标签，则标为 `human_corrected`
- 最终评测集只允许 `human_reviewed` 或 `human_corrected` 样本进入基准集

### 4. 扩充策略

第一版 `400` 条完成后，后续扩充不覆写旧样本，而是追加新批次：

- 新批次保留 `batch_id`
- 允许定期引入新 source 或新市场分布
- 基准评测时可使用“核心集 + 扩展集”双视角统计

## 评测器设计

### 1. 目标指标

研究代理第一阶段优先围绕以下指标比较：

- `precision`
  - 被系统判为市场相关的新闻中，真实市场相关的比例
- `recall`
  - 数据集中真实市场相关的新闻中，被系统保留下来的比例
- `noise_rejection_rate`
  - 数据集中噪音样本中，被系统正确过滤掉的比例

建议默认主指标为 `precision`，辅指标为 `recall` 和 `noise_rejection_rate`。

原因：

- 当前项目最先要解决的是“feed 噪音偏多”
- 若一开始把主目标设成过高 recall，代理容易通过“什么都留下”来取巧

### 2. 输出内容

每次评测至少输出：

- 指标摘要
- `false_positive` 样本列表
- `false_negative` 样本列表
- 各 `noise_type` 分布
- 与 baseline 的差异

建议输出既有人读报告，也有机器可比较的结构化结果：

- `artifacts/.../evaluation.json`
- `artifacts/.../evaluation.md`

### 3. Baseline 机制

研究代理启动前，必须先对当前主分支逻辑跑出 baseline。

所有后续实验都必须与 baseline 比较：

- 若主指标下降，则自动判失败
- 若主指标持平但辅指标明显变差，也判失败
- 若主指标提升且没有显著破坏辅指标，则允许保留候选改动

### 4. 抗投机约束

为了避免代理通过极端过滤策略“刷高 precision”，评测器需增加护栏：

- 设定最小 `recall` 下界
- 报告过滤后剩余新闻量比例
- 对“全部保守过滤”的实验直接标记为无效

## 研究代理设计

### 1. 允许改动范围

第一版研究代理仅允许修改以下类别：

- 新闻源配置
- 新闻过滤规则
- relevance 判断 prompt
- [news_ingestion.py](/Users/xiuyang/Desktop/news-caught/backend/app/services/news_ingestion.py)
- [news_signal_pipeline.py](/Users/xiuyang/Desktop/news-caught/backend/app/services/news_signal_pipeline.py)
- 与新闻相关性直接相关的同层服务

明确禁止：

- 前端目录
- 基础设施与启动链路
- 无关 API route
- 数据库底层与通用框架代码

### 2. 实验循环

研究代理每轮只允许做一个聚焦假设，例如：

- 调整 source 白名单或权重
- 增加一条规则过滤器
- 修改 relevance prompt 中的判定边界
- 优化标题/摘要去噪逻辑

固定循环如下：

1. 读取上一轮 baseline 和最近实验记录
2. 生成一个单点假设
3. 在允许范围内自动改代码或配置
4. 运行评测器
5. 记录结果
6. 决定保留还是回退

### 3. 保留规则

只有满足以下条件的实验才允许保留：

- 主指标优于 baseline
- `recall` 未跌破最低约束
- 没有明显扩大某一类关键误杀
- 测试和评测脚本都通过

否则：

- 实验结果仍记账
- 改动不进入保留状态

### 4. 自动改代码的风险控制

即使允许代理自动改代码，也不能让它像通用 agent 一样满仓修改。建议施加以下边界：

- 单轮实验只改一个明确方向
- 单轮实验只触达允许范围内的文件
- 每轮必须留下结构化 diff 摘要
- 若评测脚本失败，直接判该轮实验无效

## 研究账本设计

建议新增研究记录目录，例如：

- `docs/research/`
- `artifacts/research/`

每轮实验至少记录以下字段：

- `experiment_id`
- `timestamp`
- `baseline_id`
- `hypothesis`
- `changed_files`
- `metrics_before`
- `metrics_after`
- `decision`
- `notes`

建议同时保留一个机器易读的总表，例如 `tsv` 或 `jsonl`，作用类似 `autoresearch` 的 `results.tsv`。

原则：

- 失败实验也必须记录
- 不能只记录“成功故事”
- 后续代理在生成新实验前必须先读取最近账本，避免重复试错

## 项目结构建议

建议把这套能力放进项目内，而不是做成外部 skill：

- `backend/scripts/`
  - 抽样脚本
  - 自动标注脚本
  - 评测脚本
- `backend/data/research/`
  - 原始候选样本
  - 标注后的评测集
- `docs/research/`
  - 研究说明
  - 实验账本导出

这样做的原因：

- 研究逻辑强依赖本项目的数据结构和服务边界
- 评测结果需要与当前仓库代码直接联动
- 后续无论是手动触发还是 automation，都会更容易落地

## 分阶段实施建议

推荐分四个阶段推进：

### 阶段 1：评测基础设施

- 定义标签 schema
- 实现样本抽样脚本
- 实现 `DeepSeek` 半自动标注脚本
- 产出首版 `400` 条数据集

### 阶段 2：离线评测器

- 实现 relevance 评测脚本
- 跑出 baseline
- 形成第一版实验报告格式

### 阶段 3：受控研究代理

- 限定可改动文件集合
- 接入“单轮单假设”的实验控制器
- 让代理可自动改代码并根据评测结果决定保留或回退

### 阶段 4：持续化运行

- 增加定期扩充样本和定期评测
- 再考虑是否做 nightly research automation

只有前三阶段稳定后，才适合进入持续运行。

## 测试与验证策略

本轮设计文档落地后的后续实现最小验证建议如下：

- 抽样脚本单元测试
- 标注结果 schema 校验测试
- 评测器基线回归测试
- 研究代理实验保留/回退逻辑测试
- `conda run -n news-caught pytest backend/tests`

第一阶段实施时不要求立刻引入前端或在线运行验证。

## 关键决策

1. 先做项目内能力，不做通用 skill
   项目真正需要的是“围绕市场新闻相关性做可重复实验”的内生机制，而不是一个泛化助手。

2. 先做粗标签，不做细粒度 taxonomy
   第一目标是形成稳定闭环，而不是在标注阶段把复杂度拉满。

3. 先做半自动标注，再做自动研究
   评测集质量决定后续代理研究是否可靠，不能跳过这一步。

4. 默认主指标是 precision
   当前阶段优先降低 feed 噪音，而不是盲目追求召回。

5. 自动改代码必须有边界
   允许研究代理直接改后端相关服务，但必须在固定可改范围和固定评测规则内运行。

## 风险与后续

- 如果 `DeepSeek` 首标提示词设计不稳，第一版标注会出现系统性偏差，需要通过人工复核及时校正
- `market_relevant` 是业务定义，不是客观事实；后续可能需要逐步补充更细的正例边界说明
- 若评测集过度依赖某几类 source，代理容易对 source 分布过拟合
- 若只优化 `precision` 而缺少 recall 护栏，代理可能通过过度过滤取巧
- 当前设计尚未进入 implementation plan；需要在用户确认 spec 后再进入计划拆解
